Choosing the Right Agent

Start from the activity, not the agent name: • Plan research before talking to users → Research Planner • Make sense of interviews and test results → Insights Synthesizer • Structure experiences, screens or a prototype → Experience Architect • Gather project, code and standards context → Context Builder • Define the business need → BRD Builder • Define what the product must do → PRD Builder • Turn requirements into epics and stories → Jira Backlog Manager • Turn requirements into an implementation ready spec → Spec-Clarify • Break the spec into tasks → Task-Planner • Write code and unit tests → Task-Implementor • Review code and pull requests → Code Review • Test APIs → API Testing • Test UI behaviour → Functional Testing • Deploy to Azure → Azure-Deploy

Inputs and Context

Good input is anything you'd be comfortable handing to a new colleague on their first day and saying, "Work from this." The agent has no memory of past meetings, no hallway chats and no sense of "how we do things here." What you give it is everything it knows. Consider these 4 criteria: Approved: Has someone accountable signed this off? Current: Is this the latest version, with nothing newer that replaces it? Accessible: Can the agent actually open and read it? Specific: Is it detailed enough for this task?

More isn't better. An agent can only hold so much in view at once, and every extra document competes for its attention. Past a certain point, you're not adding knowledge, you're adding noise. Think of handing a new colleague a 40 page pack and saying "base your answer on this." They would spend their effort sorting what matters from what doesn't, and some of it would slip through.

Tell the agent what you are missing so that it does not make its own assumptions. When the agent lacks something, it has two options: stop and ask, or fill the hole with a plausible assumption. If you don't tell it which to do, it may pick the second. The assumption then gets built on by every step that follows, and by the time someone spots it, it is baked into requirements, tasks and code.

Writing Prompts

There are 5 criteria to consider. Task: What do you want done? "Turn this BRD into a product requirements document." Input: What should it work from? "Use the attached approved BRD and the project context." Output: What should the result look like? "Tag every story P0, P1 or P2, and mark the MVP boundary." Rules: What must it keep or avoid? "Keep traceability to the BRD. Do not add features that aren't in it." Unknowns: What should it do when it's unsure? "List anything you can't confirm as an open question. Do not assume." Stop point: What should it not do yet? "Do not create anything in the backlog. Give me the plan to review."

Ask the agent to show its working. Follow up with "what is this based on?" for the agent to critique its own response. When you're unsure, you're really asking one of five things: where did this come from, what did you assume, what did you miss, how confident are you, and what would change your answer.

Work in layers, not in one go. Start on the component level by describing exactly what you want the agent to create and how the interaction will be. You can also share image or link references to sites that has what you have in mind for the agent to learn from.
