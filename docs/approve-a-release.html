What are you reviewing?

You are reviewing the release candidate and everything that justifies releasing it. That means the build artefacts, the accepted test evidence, the quality and security results, and the deployment package, version and logs.

Each approver answers a different question, so know which seat you are in.

  • FDA: Ensure quality and security evidences are strong enough to proceed
  • FDE: Ensure release candidate is complete, traceable and ready to ship
  • PO: Ensure product suitability for real users

When the output is weak

Do not approve on trust or on deadline pressure. If evidence is missing, send it back to the stage that owns it rather than patching it at the gate, so testing gaps go to the Quality Engineer, code issues go back through implementation and review, and configuration problems go to whoever owns the deployment setup.

If the deployment fails or reports something unexpected, stop the promotion, read the deployment logs and decide whether the fault is in the package, the configuration or the environment. If the rollback path is unclear, treat that as a blocker in its own right, because a release you cannot undo needs a higher bar than one you can.

Handoff

Once deployment is approved and complete, the release moves into Operate & Learn, where the Ops or System Manager keeps an ongoing review. Production learning then feeds back into the context, requirements and tests for the next increment. Keep the release evidence, since brownfield work in particular depends on it later.
