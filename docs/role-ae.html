As an Application Engineer,

you are accountable for the code that ships,

whoever or whatever wrote it.

These are where you are most involved in:

01 01
Discover / Context

Assemble requirements, design and brownfield context as input to the PDLC.

02 02
Specify

Turn approved requirements into a buildable specification with clear priorities and business decisions.

03 03
Plan

Validate that scope and delivery plan align with business priorities before work begins.

04 04
Tasks

Review task breakdowns and ensure acceptance criteria match your approved specification.

05 05
Implement

Stay available to unblock decisions as agents build to spec — scope creep still needs your veto.

06 06
Test & Validate

Confirm that what was built actually delivers the value stated in the PRD, not just that it works.

07 07
Build / Ship

Give deployment sign-off once you’re satisfied that the right thing ships to the right users.

08 08
GreenLane CI/CD

Ensure the pipeline and backlog stay aligned with your approved priorities through each build cycle.

09 09
Operate & Learn

Own whether the expected value showed up. Use what the squad learns to feed the next PDLC cycle.

Stage 4. Tasks

What you are responsible for

Before an agent writes anything, someone has to describe the work clearly enough that it can be done correctly. That is increasingly your job. Writing a bounded specification forces you to think the problem through first, and it is one of the best ways to build engineering judgement.

Assigned tasks in tasks.md

Is each one clearly scoped, with the context it needs and no hidden decisions inside it?

Task fit for an agent

Does this look simple but touch code agents tend to mishandle? Flag it to the FDE, who decides whether it is agent-executed, human-led or hybrid.

Unit test and pre-submit check plans

Are they planned alongside the implementation? Ask for them if they are missing.

Stage 5. Implement

What you are responsible for

You remain accountable for implementation and pull request quality, even when an agent produced the change. That means you understand what the code does, you resolve the failures, and you only put a pull request forward when it is genuinely ready. Reviewing agent output is a core part of the job, and for engineers earlier in their careers it is also how judgement gets built.

Agent generated code and unit tests

Do they trace to approved tasks, respect the architecture and standards, and contain nothing nobody asked for?

Implementation and verification evidence

Do the focused checks pass, and do the records show the commands and results?

Security, privacy and design fidelity

Have secrets, input validation, sensitive data and the approved designs been respected?

Stage 6. Test & Validate

What you are responsible for

You make the fixes when testing finds a real defect. The test agents report problems but must not change application code to make tests pass, so a genuine defect comes back through you, goes through implementation and review again, and is not patched at the test stage.

Failed API and functional test cases

Is this a real defect, a wrong test or a gap in the spec?

Contract drift

Does the API behave differently from its contract? Raise it with the FDE and FDA, who decide whether the code or the contract is wrong.

Blocked or skipped cases

Is something in the implementation or the environment preventing the test?

These are the agents you'll most likely work with:

Task-Implementor

Executes individual tasks from tasks.md — writing code, unit tests and verification records — and submits output for engineering code review.

Code Review

Reviews agent-generated code against approved tasks, architecture standards and security baselines, and flags issues for the engineer to resolve before merging.

Task-Planner

Breaks an approved specification into a sequenced task list with dependencies, acceptance criteria and pre-submit check plans ready for engineering review.

API Testing

Runs contract and integration tests against API endpoints, reports failures and contract drift back to the engineer for triage and resolution.

Functional Testing

Executes end-to-end functional test suites against the running application, reports defects and blocked cases back to the engineer without modifying application code.
