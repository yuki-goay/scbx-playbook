Stage 1. Discover / Context

What you are responsible for

Agents do not share the squad's background knowledge. They cannot know your architecture decisions, conventions or unwritten rules unless someone makes them explicit, and that someone is you. This is where context engineering starts. You decide which architectural knowledge, standards and constraints an agent needs, so that it acts consistently with engineering intent instead of confidently guessing.

Project context package

Is the context authoritative, current and relevant, or is outdated and conflicting material about to mislead the agents?

BRD and PRD (greenfield)

Is the architecture decision stated with a rationale, and are the technical, security and compliance constraints realistic?

Existing code and architecture (brownfield)

Confirm the impact, constraints and reusable components.

Stage 2. Specify

What you are responsible for

You make sure the specification respects the boundaries agents and engineers must work within. As the accountable technical role, you help resolve the gaps and conflicts the specification raises, so that an unanswered technical question never turns into a quiet implementation assumption.

spec.md

Does it fit the architecture, and are contracts, validation and error handling covered where they apply?

Clarifications

Which open points need a technical answer?

Scope declarations

Does the spec state whether APIs and UI are in scope? The testing agents depend on it and will stop without it.

Stage 3. Plan

What you are responsible for

You own the solution approach. The plan decides how the specification becomes a design, what the architecture impact is, and in what order the work happens, which makes this the most consequential architecture gate in the lifecycle. No implementation begins until the approved plan satisfies the planning gate.

plan.md

Does the solution respect your boundaries, patterns and constraints, and has the agent introduced design decisions that nobody approved?

Architecture and impact analysis

Are compatibility, interface and regression risks understood, and for modernisation, are coexistence, migration and rollback covered?

Compliance Reviewer findings

Have all findings been addressed before implementation starts?

Stage 6. Test & Validate

What you are responsible for

You hold the Quality & Security gate. The Quality Engineer accepts the test evidence, and you decide whether that evidence, together with the security and architectural picture, justifies moving towards release.

Accepted test evidence

Is coverage sufficient, are failures, skipped cases and blockers explained, and does contract drift have an owner?

Security, privacy and compliance results

Have the controls been met, and are remaining risks written down with an owner?

Subtle architectural violations

Does the code pass its tests while quietly breaking the architectural intent? Escalate it — this is the kind of problem only you are placed to spot.
